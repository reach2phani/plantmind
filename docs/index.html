Case study · AI for manufacturing ● Draft: updated as work continues

An AI assistant that knows the machine, not just the manual.

An operator types "WM-101 wire feed stuttering, third time this shift". PlantMind searches the plant's own procedures, maintenance records and shift logs, walks a map of how that machine fails, and returns a sourced investigation report: how critical it is, what to do first, and what never to do.

01

The problem

When a machine faults at 2 a.m., the answer usually exists somewhere: a procedure, an old non-conformance report, a note in last month's shift log, or the head of a senior operator who isn't on shift. Finding it takes hours. Guessing is faster, and guessing is how the same fault comes back.

Scattered knowledge

Procedures, work instructions, quality reports and shift logs live in different places, in different formats.

Tempting wrong fixes

Some faults have an obvious response that makes things worse. On the welder, tightening the drive rolls feels right and hides the real wear.

Tribal knowledge

An experienced operator's fix gets shared by phone and never written down, so the next shift starts from zero.

Goal: a report an operator can follow like a checklist, where every fact can be traced to its source, and the system says "I don't know" instead of inventing.

04

Retrieval: finding the right page

Documents are cut into pieces, turned into meaning-vectors, and stored with labels: plant, line, machine, document type. Search always stays inside the machine being asked about.

Never answer from the wrong machine

If nothing is found for the machine, the answer is "no documents for this machine", never a search across every machine. A plausible answer from the wrong manual is worse than no answer.

Each specialist reads one kind of document

Alarms read shift logs, the maintenance specialist reads work instructions, and so on. Each gets a narrow, relevant slice instead of one big mixed pile.

Measured, not assumed

18 labelled questions: the right piece was found in the top 12 for 18/18, in the top 3 for 14/18 (MRR 0.68).

Known weakness

Pieces are cut every ~1,000 characters, so a mandatory last step can fall just past a cut. Exact codes like a part number are also weak for meaning-based search. Both are planned for Phase 3.

05

The knowledge graph: how the machine fails

Search finds pages. It doesn't know that a liner replacement requires a burn-in, or that one fault triggers a quality hold. The graph stores those links, built from the documents and checked by hand, so the report can't forget them.

  1. The machine. WM-101, a MIG welder on Fabrication Line 1.
  2. The fault it matched. Wire feed motor overload, from the operator's words.
  3. The real cause. Worn drive rolls and liner, as recorded in the non-conformance report.
  4. The trap. "Keep tightening the tension" feels right, and hides the wear. The graph flags it as a known wrong response.
  5. The fix. Replace the liner, from the work instruction.
  6. The step people forget. Burn-in is mandatory after a liner change, and some wire wobble during it is expected, not a new fault.
  7. Safety first. Lockout (LOTO) before any work, and parts welded during the fault are held for inspection.
The graph is an overlay: if it's unavailable, the investigation still runs on documents alone. Operator knowledge only enters the graph after a person approves it in a review queue. Nothing is written automatically.
06

Reasoning and rules: who to believe

Sources disagree. An operator's tip can contradict the procedure. So every fact carries a trust level, and the level decides what it is allowed to do in the report.

TIER 1
Documented specification

Values and steps from the SOP and work instructions, confirmed by the graph.

sets values & steps
TIER 2
Document findings

Non-conformance reports, shift log history.

sets causes & steps
TIER 3
Approved operator knowledge

Reviewed and approved by a person; cited by name.

can lead the action
TIER 4
Unreviewed operator tip

Captured but not yet reviewed.

a lead to check, never a step
  • Criticality has a floor from the graph (code, not AI)
  • A visible ⚠ if an unreviewed tip reaches the repair steps
  • The AI supervisor can add searches, never remove required ones
  • The review step can never change the criticality rating
  • Work-order cost is computed in code, so the model can't talk it into a cheaper approval tier
  • Contradictions are shown side by side and flagged for an engineer, never silently resolved
07

How it's measured

Every change is measured before and after, on the same questions. Code checks anything exact (a value, a step, a time); an AI judge checks judgement (did it warn against the trap?); each case runs three times to catch inconsistency.

ablation

Graph value test

6 hard cases × 3 runs, with the graph switched off and on. Scores required facts, made-up specifics, and consistency.

regression

promptfoo suites

Docs, Shift and Investigation questions with code checks and a judge model. Known failures are tracked separately from new ones.

health

Graph health & routing

8 structural rules for the graph (no orphans, full hand-over, relevance), plus a routing check: did each case search what it needed?

09

Failure cases: what broke, and what it taught

The most useful results were the failures. The second machine, FL-101 (a bottle filler, a different industry), was added with one rule: no code changes for it. Anything that only worked for the welder had to be fixed for every machine.

fixedAn unreviewed tip beat the procedure
SymptomAn operator's untested "raise tension 18 → 22" appeared as a repair step in 14 of 18 reports.
CauseThe prompt said "expert fix first", with no difference between reviewed and unreviewed knowledge.
Fix & lessonTrust tiers, labelled in code: 14/18 → 1/18. Trust must be explicit, not implied by order.
fixedThe graph was fetched but half of it never reached the AI
SymptomWith the graph on, reports still missed facts that were in the graph.
CauseThe hand-over text used an allow-list of properties, so new facts were silently dropped.
Fix & lessonHand over every fact of the matched fault: 70% → 90%. Check what the model actually receives.
fixedShift questions assumed every date was in 2025
SymptomOn FL-101, "alarms on the night of 10 September" returned "no events on 2025-09-10". The logs are from 2026.
CauseA missing year defaulted to 2025, because every welder log happened to be from 2025.
Fix & lessonTake the year from the logs by exact lookup, and tell the operator when other years exist. One year of test data hides date bugs.
fixedSafety rules written for a welder
SymptomBroken glass in the filler was rated HIGH. The SOP itself says CRITICAL.
CauseCRITICAL listed only "electrical, fire, fumes", which are welding hazards.
Fix & lessonAdded injury and foreign material, and "never rate below the document's own rating". Rules quietly encode the machine they were written for.
fixedAn empty graph was reported as "verified"
SymptomAn FL-101 report claimed "knowledge graph (verified) confirms SOP steps", but no fault graph existed yet.
CauseThe machine's own node counted as "graph available", so the AI got an empty section and filled the gap.
Fix & lessonThe graph only counts with real knowledge. An empty context section invites invention.
fixedThe test itself was wrong
SymptomAfter the date fix, the answer "missed" the valve numbers.
CauseThat seal change is in the next morning's log. The answer key asked for data from the wrong day.
Fix & lessonCorrected the answer key. Answer keys need checking too.
openThe mandatory last step falls past a cut
SymptomWelder: burn-in after a liner change is missed. Filler: the 10-minute rinse after a seal change is missed, and normal overfill was called a fault.
CauseDocuments are cut every ~1,000 characters, and the last steps land in a piece search doesn't return.
PlanCut by section with headings kept (Phase 3), and let the graph carry must-do steps. Same failure on two machines: a general weakness.
openA false match merged two different faults
SymptomA gas-flow finding was approved as "reinforcing" an unrelated contact-tip pattern, and its content was lost.
CauseReinforcement only increases a count, and the reviewer isn't shown what it merges into.
PlanShow "will merge into: …" before approval, and keep both texts.
10

Production-hardening decisions

  • Model choice lives in two settings (rollback is a two-line change, not a code edit)
  • A shared token budget queues calls (free-tier limits never crash a report)
  • Specialists run 2 at a time (avoids rate-limit bursts)
  • Graph, tracing and citation counting fail silently (extras never block the core answer)
  • Every AI call is logged with real token counts
  • Work orders: server-side state machine, full audit trail
  • Human review before any operator knowledge is trusted
  • Tracing of every step in LangSmith
